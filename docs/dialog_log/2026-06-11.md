## 3. 태그 모니터링 — Phase 2 (이상 필터 9종) + 조회 속도 최적화
**사용자 요청**: "이어서 진행해줘, 그리고 태그 데이터가 조회가 늦게 뜨는데
속도 최적화 방안도 검토해줘"

**성능 최적화 (조회 지연 해결)**:
- 원인: 현재값 조인 `DISTINCT ON (tagsn)` CTE 가 7일 윈도우 1,470만 행 전량
  스캔 (Merge Append→Unique). EXPLAIN ANALYZE ~8,445ms. PostgreSQL 은
  loose index skip-scan 미지원이 근본 원인.
- 해결: `LEFT JOIN LATERAL` (태그별 `idx_tag_raw_tagsn_time` 시크 + `LIMIT 1`).
  curl 측정 — 기본 조회 ~12ms, 현재값 정렬 최악 ~31ms (≈300배 개선).

**Phase 2 구현**:
- 백엔드 (`slm/endpoints/tags.py` + `ai_server.py`)
  - `init_tags(get_db, get_scan_cache, get_balance_cache)` 캐시 getter 주입
    (순환 import 회피, dashboard 와 동일 패턴)
  - `_build_anomaly_maps()`: scan 캐시 `data_quality_issues`→태그,
    `equipment_failure_impacts[].affected_tags`→태그,
    `cross_facility_mismatches`→시설(상·하류), balance 캐시 비정상 edge→시설
  - `_categories_for()`: 태그별 scope=tag/facility 카테고리 리스트 구성
  - 엔드포인트 `anomaly`/`only_anomaly` 파라미터 — 하이브리드:
    필터 없으면 SQL 페이지네이션(fast path), 있으면 전량 hydrate→Python
    필터/이상개수 정렬/페이지네이션. `anomaly_ready` 플래그 응답
- 프런트
  - `AnomalyFilterChips.tsx` 신규 — "이상만" 토글 + 9 카테고리 칩 (OR 필터)
  - `TagMonitoringTable`: "이상 상태" 정렬 컬럼 + Badge (태그=destructive,
    시설=outline+"(시설)", title=상세). `tag.ts` AnomalyCode 9종 + 카테고리 정의
  - `page.tsx`: anomaly/onlyAnomaly 상태 + URL 동기화(`?anomaly`/`?only_anomaly`)
    + 캐시 미준비 시 amber 안내

**검증**:
- curl: 9 카테고리 각각 카운트 + anomaly_count 정렬(다중 카테고리 우선) 확인
- Playwright: `센서 무응답` 칩 클릭 → 전체 2,700→62건, URL `?anomaly=sensor_dead`,
  요청 `?anomaly=sensor_dead&page=1&page_size=50` 200. Badge scope 구분 렌더,
  툴팁("7일간 845건 전부 val~0" 등) 정상

**상태**: Phase 2 완료·커밋. Phase 3(트랜드 보기 컨텍스트 메뉴)/4(다듬기) 대기.

## 4. 이상 카테고리 9→6종 — DI 발 설비고장·전원이상·통신이상 제거
**사용자 지적**: "설비고장 DI 활성"이라 해서 태그유형 DI로 찾으니 태그가 안 나옴.
→ 원인 분석 결과 설비고장/전원이상/통신이상(B소스)은 DI 신호 태그(예 밸브 FAULT)가
val=1이면 그 **현장+시설 측정 태그 알파벳 상위 5건**에 전파하는 방식. 아날로그·디지털
혼재 + 기기 단위 깨짐 + 임의 5건이라 오해·노이즈. 트리거 DI 태그는 스캔 대상이
아니라 배지 목록에 없음(그래서 DI 필터로 안 보임).
**사용자 결정**: "3종 모두 제거해줘".

**변경**:
- 백엔드 `tags.py` `_ANOMALY_LABELS` 에서 equip_fault/power_fault/comm_error 삭제
  (`_ANOMALY_CODES` 파생 → equipment_failure_impacts 루프가 자동 스킵, network_down만 유지)
- 프런트 `tag.ts` AnomalyCode 6종 + ANOMALY_CATEGORIES 6개, `page.tsx` ANOMALY_ALL 6개
- 사양 `tag-monitoring-spec.md` §3 6종 표 + §3.0 제외 사유 + 변경이력 v1.2
- 근거: DI 장애 신호는 트리거 DI 태그 자체 행(현재값=1 + 알람 컬럼)에서 직접 확인 가능
- 남긴 6종: 센서무응답·데이터홀딩·데이터없음(태그) + 교차검증·물수지(시설) + 네트워크단절(기기)

**상태**: 백엔드 reload 후 이상 캐시 재빌드(~161s) → 카테고리 집합에 제거 3종 부재 확인.

## 5. 태그 모니터링 — 현재값 비교 필터 추가
**사용자 요청**: "필터링에 데이터값을 비교하는것도 있으면 좋겠어. 몇 이상, 이하, 같음 등"

**구현**:
- 백엔드 `tags.py`
  - `_VALUE_OPS` 6종 연산자 맵 (gte/lte/gt/lt/eq/ne, lambda 비교)
  - 엔드포인트 `value_op`/`value` 파라미터 — 현재값(LATERAL 조인)은 fast-path
    SQL 카운트로 못 거름 → `full_scan = anomaly_active or value_fn` 으로 전체 조회
    경로 진입, Python 에서 `current_value` 필터링. NULL 은 모든 연산 불일치.
- 프런트
  - `tag.ts`: `ValueOp` 타입 + `VALUE_OPS` 라벨 배열(이상≥/이하≤/초과>/미만</같음=/다름≠)
    + `TagMonitoringQueryParams` 에 `value_op`/`value`
  - `tag-api.ts`: `fetchTagMonitoring` qp 에 value_op/value 추가
  - `page.tsx`: 현재값 셀렉트(비교 안 함 + 6연산자) + 숫자 입력(연산자 없으면
    비활성), 초기화에 포함, load 의존성·setPage(1) 연동

**검증**:
- curl: gte 100→126건(적산유량 등), eq 0→1471건(디지털), lt 0→0건(음수 없음)
- Playwright: 이상(≥) + 100 → 전체 127건, 표시값 전부 ≥100 (371,743 적산유량,
  725.62 순시유량 등). 이상 칩도 6종만 표시(9→6 제거 UI 동시 확인)

**상태**: 완료. 커밋 대기.
