## 3. 태그 모니터링 — Phase 2 (이상 필터 9종) + 조회 속도 최적화
**사용자 요청**: "이어서 진행해줘, 그리고 태그 데이터가 조회가 늦게 뜨는데
속도 최적화 방안도 검토해줘"

**성능 최적화 (조회 지연 해결)**:
- 원인: 현재값 조인 `DISTINCT ON (tagsn)` CTE 가 7일 윈도우 1,470만 행 전량
  스캔 (Merge Append→Unique). EXPLAIN ANALYZE ~8,445ms. PostgreSQL 은
  loose index skip-scan 미지원이 근본 원인.
- 해결: `LEFT JOIN LATERAL` (태그별 `idx_tag_raw_tagsn_time` 시크 + `LIMIT 1`).
  curl 측정 — 기본 조회 ~12ms, 현재값 정렬 최악 ~31ms (≈300배 개선).

**Phase 2 구현**:
- 백엔드 (`slm/endpoints/tags.py` + `ai_server.py`)
  - `init_tags(get_db, get_scan_cache, get_balance_cache)` 캐시 getter 주입
    (순환 import 회피, dashboard 와 동일 패턴)
  - `_build_anomaly_maps()`: scan 캐시 `data_quality_issues`→태그,
    `equipment_failure_impacts[].affected_tags`→태그,
    `cross_facility_mismatches`→시설(상·하류), balance 캐시 비정상 edge→시설
  - `_categories_for()`: 태그별 scope=tag/facility 카테고리 리스트 구성
  - 엔드포인트 `anomaly`/`only_anomaly` 파라미터 — 하이브리드:
    필터 없으면 SQL 페이지네이션(fast path), 있으면 전량 hydrate→Python
    필터/이상개수 정렬/페이지네이션. `anomaly_ready` 플래그 응답
- 프런트
  - `AnomalyFilterChips.tsx` 신규 — "이상만" 토글 + 9 카테고리 칩 (OR 필터)
  - `TagMonitoringTable`: "이상 상태" 정렬 컬럼 + Badge (태그=destructive,
    시설=outline+"(시설)", title=상세). `tag.ts` AnomalyCode 9종 + 카테고리 정의
  - `page.tsx`: anomaly/onlyAnomaly 상태 + URL 동기화(`?anomaly`/`?only_anomaly`)
    + 캐시 미준비 시 amber 안내

**검증**:
- curl: 9 카테고리 각각 카운트 + anomaly_count 정렬(다중 카테고리 우선) 확인
- Playwright: `센서 무응답` 칩 클릭 → 전체 2,700→62건, URL `?anomaly=sensor_dead`,
  요청 `?anomaly=sensor_dead&page=1&page_size=50` 200. Badge scope 구분 렌더,
  툴팁("7일간 845건 전부 val~0" 등) 정상

**상태**: Phase 2 완료·커밋. Phase 3(트랜드 보기 컨텍스트 메뉴)/4(다듬기) 대기.
