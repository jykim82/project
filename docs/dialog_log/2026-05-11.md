## 진단

`tb_report_item.photo_urls` JSONB 12 photo objects 감사:

| 종류 | 건수 | 파일시스템 | 상태 |
|------|------|-----------|------|
| REAL_HASH (`[0-9a-f]{32}.jpg/png`) | 5 | 존재 | 정상 표시 |
| TEST_DUMMY (`test-*.jpg`) | 7 | **부재** | 404 |

원인: P1 보고서 자동화 테스트 (04-25~28) 시 가짜 파일명만 INSERT, 실제 파일은
업로드 안 됨. `tb_task_master.photo_urls` / `resolution_photo_urls` 의 실제
hash 파일은 정상.

영향: report 1 (item 1, 2, 3), report 2 (item 4), report 3 (item 5).

## 조치 (Option A — 깨진 항목만 제거)

```sql
UPDATE tb_report_item
SET photo_urls = NULLIF(
  (SELECT COALESCE(jsonb_agg(p), '[]'::jsonb)
   FROM jsonb_array_elements(photo_urls) p
   WHERE p->>'url' NOT LIKE '%/test-%'),
  '[]'::jsonb
), updated_at = NOW()
WHERE photo_urls IS NOT NULL
  AND EXISTS (SELECT 1 FROM jsonb_array_elements(photo_urls) p
              WHERE p->>'url' LIKE '%/test-%');
```

결과:
- 5 rows UPDATE
- 12 photo objects → 5 (test-* 7건 제거, 실제 hash 5건 보존)
- 남은 test-* 0건 ✓
- item 1, 2: 3 → 1 (hash 사진 보존, dummy 제거)
- item 3, 4, 5: 1 → 0 → photo_urls NULL 처리

데이터 손실 없음 — 모든 실제 hash 사진과 그 캡션·source·taken_at 메타 보존.
