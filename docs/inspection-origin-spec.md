# 점검 기원(일상/요청) 사양 v1 — Migration 0135

점검에는 **기원이 두 가지** 있다 (2026-07-28 사용자 정의):

```
상황 1 (일상)                        상황 2 (요청)
일상 점검 ──발견──> 고장 조치        고장 이벤트 ──요청──> 점검 수행
```

**관련**: `docs/report-spec.md`(일 점검 보고서),
`docs/fault-category-policy.md`, `docs/equipment-fault-tracking-spec.md`

---

## 1. 원칙 — "기록은 하나, 문서는 기원 따라"

- **고장 카운트의 정본은 기록**(`tb_task_master`)이다. MTBF·설비 건강성·
  교체 우선순위는 전부 기록에서 나온다 — 보고서를 만들지 않아도 집계에는
  전부 잡힌다.
- **보고서 별도 작성을 강제하지 않는다.** 점검 중 발견·조치한 고장 때문에
  장애 조치 보고서를 따로 쓰게 하면 현장이 기록 자체를 안 하게 된다.
- 같은 기록이 여러 보고서에 실려도 **집계는 1건** — 기록 기반이므로
  이중 집계가 구조적으로 없다.

## 2. 데이터 모델 (0135)

| 필드 | 내용 |
|---|---|
| `inspection_type` | 값 체계 확정: **`일상`**(정기 순회) / **`요청`**(고장 이벤트로 수행). 기존 컬럼 재사용, NULL=체계 도입 전 기록 (소급 추정 금지) |
| `linked_task_id` (신규) | 요청 점검을 유발한 **고장 건 task_id**. 부분 인덱스로 역추적 |

## 3. 문서 편입 규칙

| 기록 | 일 점검 보고서 | 장애 조치 보고서 |
|---|---|---|
| 일상 점검 | ✅ 본래 자리 | — |
| 점검 중 조치한 고장 (상황1) | ✅ 후보에 포함 — 「점검 중 조치」 배지 | 중대 건만 선택 |
| 요청 점검 (상황2) | ✅ 「요청 점검」 배지 | (P2) 링크된 고장 항목의 조치 경과에 표시 |

구현: `GET /reports/candidates?category=점검&include_faults=true` — 일 점검
보고서의 항목 후보에 같은 기간 고장보고를 포함한다 (프런트는 일 점검일 때
자동 적용). 실측: 4~7월 후보 25건 = 점검 4 + 고장 21.

## 4. 입력 동선 (P1)

작업 등록 폼(TaskFormDialog) — 카테고리가 '점검'일 때:
- **점검 기원** 선택 (일상/요청, 선택사항 — 강제하면 기록을 막는다)
- '요청' 선택 시 **유발 고장 건** 선택 (진행중 고장보고 목록에서)

## 5. P2 (향후)

- 채팅 자연어 점검 기록에 기원·링크 반영 ("죽동 펌프 고장 건 점검했어")
- 장애 조치 보고서에서 링크된 요청 점검을 조치 경과로 표시
- 점검 도래(inspection-cycle-spec) 계산에 기원 구분 활용
