## 1. 왜 하는가

수운영은 3교대인데 **인계 화면이 없다.** 지금은 교대할 때 알람 목록·장애
이력·메모·일정을 각각 열어보고 구두로 넘긴다. 넘겨야 할 것이 화면마다
흩어져 있으니 빠뜨리는 게 생긴다.

데이터는 **이미 전부 DB 에 있다.** 새로 쌓을 게 없고, 모으는 화면만 없다.

| 넘겨야 할 것 | 이미 있는 곳 |
|---|---|
| 근무 중 발생·해소된 경보 | `tb_equipment_alarm_report` |
| 아직 안 끝난 경보 (이월) | 〃 (`alarm_status='진행중'`) |
| 미확인 경보 | 〃 (`alarm_confirm_yn<>'Y'`) |
| 근무 중 등록·완료된 장애 조치 | `tb_task_master` (`task_category='고장보고'`) |
| 진행중인 작업 (이월) | 〃 (`status='진행중'`) |
| 근무 중 남긴 업무 메모 | `tb_memo` |
| 다음 근무 예정 일정 | `tb_user_schedule` |
| 반복 경보 상위 | `/crisis/alarm-chattering` 재사용 |

**서버 비용**: 집계 SQL 몇 개. 신규 테이블·배치·모델 없음
(저사양 서버 전제).

## 2. 근무 구간 정의

### 2.1 경계는 config 로 분리한다
교대 시각은 고객마다 다르다. 하드코딩하지 않고
`tb_comm_code(grp_cd='SITE_SETTING', comm_cd='SHIFT_BOUNDARIES')` 에 둔다.

```
comm_val = "08:00,16:00,00:00"    -- 기본값 (3교대)
```

- 값은 **하루를 자르는 경계 시각의 목록**이다. N 개면 N 교대.
- 비었거나 파싱 실패면 **24시간 단일 근무**로 본다 (교대 개념이 없는
  현장도 화면은 동작해야 한다).
- 경계는 정렬해 사용하며, 자정을 넘는 구간(예: 16:00~08:00)을 허용한다.

### 2.2 조회 구간 선택
- `shift=prev` (기본) — **직전 근무**. 교대 직후에 여는 게 정상 사용이므로
  기본을 "지금 속한 근무"가 아니라 직전으로 둔다.
- `shift=current` — 현재 근무 (근무 중간 점검용)
- `hours=N` — 경계 무시하고 최근 N 시간 (임의 구간)

## 3. 백엔드

### 3.1 `GET /shift/handover` (신규)
`slm/endpoints/shift_handover.py` — 알람·작업·메모·일정을 가로지르므로
기존 모듈 어디에도 속하지 않는다. 별도 모듈로 둔다.

**파라미터**: `shift`(prev|current, 기본 prev), `hours`(1~168, 지정 시 우선)

**응답**
```jsonc
{
  "status": "OK",
  "window": {
    "start": "2026-07-27 00:00:00",
    "end":   "2026-07-27 08:00:00",
    "label": "야간 (00:00~08:00)",
    "mode":  "shift" | "hours"
  },
  "alarms": {
    "opened": 12,          // 구간 내 발생
    "resolved": 9,         // 구간 내 해소
    "carried_over": 44,    // 구간 끝 시점 기준 진행중 (넘겨받을 것)
    "unconfirmed": 40,     // 그중 미확인
    "by_category": [{ "category": "네트워크", "count": 8 }],
    // (현장, 메시지) 로 접은 목록 — 심각도 → 최신순
    "items": [{
      "sitename": "죽동", "alarm_msg": "죽동(배) 탁도계 통신이상",
      "count": 38,              // 구간 내 반복 횟수
      "last_at": "…", "unconfirmed": 38,
      "facilitytype": "배수지", "alarm_category": "네트워크",
      "alarm_severity": "주의", "tagsn": "…"
    }]
  },
  "faults": {
    "opened":   [ /* 구간 내 등록된 고장보고 */ ],
    "resolved": [ /* 구간 내 완료 처리된 것 */ ],
    "ongoing":  [ /* 아직 진행중 — 넘겨받을 것 */ ]
  },
  "memos":    [ /* 구간 내 작성 */ ],
  "upcoming": [ /* 다음 근무 구간에 예정된 일정 */ ],
  "repeat_top": [ /* 반복 경보 상위 3 — 구간이 아니라 최근 30일 기준 */ ]
}
```

### 3.2 설계 결정

**`carried_over` 는 "구간 내"가 아니라 "구간 끝 시점의 상태"다.**
인수자가 알아야 할 건 "내가 지금 뭘 넘겨받는가"이지 "지난 8시간에 몇 건이
진행중이었나"가 아니다.

**`repeat_top` 만 구간이 아닌 30일 기준이다.** 반복 경보는 한 근무 안에서
판단할 수 없다 — 죽동 탁도계처럼 몇 달째 반복되는 것이 대상이다.
화면에도 "최근 30일" 을 명시한다.
(`docs/alarm-chattering-spec.md` §6 에 예고된 연동)

**`upcoming` 은 다음 근무 구간만 본다.** 일주일치 일정을 인계 화면에 쏟으면
읽히지 않는다. 인수자가 자기 근무 중에 할 일만 넘긴다.

**경보 목록은 `(sitename, alarm_msg)` 로 접는다.** 접지 않으면 채터링 한
건이 목록을 통째로 먹는다 — 첫 구현에서 상위 10건 중 9건이 죽동 탁도계였고,
접은 뒤 48건이 8그룹이 되어 7개 현장이 드러났다. 인계 화면은 30초 안에
읽는 것이라, 접지 않으면 기능 자체가 성립하지 않는다.
원본 행은 그대로 두고 표시만 접는다 (`docs/alarm-chattering-spec.md` §2.1
과 같은 처방).

**AI 서술은 넣지 않는다 (v1).** 집계 숫자와 목록으로 충분하고, 폐쇄망 로컬
LLM 호출은 교대 시점의 즉시성을 해친다. 필요해지면 P2 에서 기존
`report_summarizer` 를 붙인다.

## 4. 프런트

### 4.1 위치 — `/reports/shift-handover` (보고서 그룹 M005-5)
인수인계는 **읽고 넘기는 산출물**이라 보고서 계열이 맞다. 경보관리에 두면
"경보 화면"이 되어 장애·메모·일정이 곁다리로 보인다.

### 4.2 구성
1. **구간 헤더** — `직전 근무 / 현재 근무 / 최근 N시간` 토글 + 구간 표시
2. **넘겨받는 것** (최상단) — 진행중 경보 · 미확인 경보 · 진행중 작업.
   이게 인계의 본체라 맨 위에 둔다.
3. **이번 근무에 있었던 일** — 발생/해소 경보, 등록/완료된 장애, 메모
4. **다음 근무 예정** — 일정
5. **반복 경보 상위 3** (최근 30일) — 반복 경보 탭으로 이동 링크

### 4.3 인쇄
기존 보고서와 같은 경로(브라우저 인쇄 CSS)를 쓴다. 서버 측 PDF 를 새로
들이지 않는다 (`docs/report-spec.md` §5.5, 폐쇄망 반입 비용).

## 5. 이 사양이 하지 않는 것

- **근무자 배정·근태 관리 없음.** 누가 어느 근무인지는 이 제품의 범위가
  아니다. 구간만 계산하고, 인계 확인 서명 같은 것도 두지 않는다.
- **자동 알람 해제·억제 없음.** 인계했다고 알람이 정리되지 않는다
  (`memory/feedback_no_auto_alarm_link.md`).
- **인계 내용 저장 없음 (v1).** 화면은 매번 DB 에서 다시 계산한다.
  "이 시점의 인계본"을 남길 필요가 생기면 P2 에서 `tb_report` 에 스냅샷.
