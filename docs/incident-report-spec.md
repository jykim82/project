# 상황보고 1보/2보 사양 v1 — 로드맵 D P1

사고 발생 시 **공문 초안을 자동 채움**으로 만들고, 담당자가 편집해 확정한다.
`/reports/incident` (M005-6). Migration 0133.

**관련**: `docs/report-spec.md`(기존 보고서 — 출력·확정 흐름의 원형),
`slm-feature-roadmap-draft.md` §3.D·부록 A.3

---

## 1. 원칙

- **자동 채움은 생성 시점 1회.** 이후엔 담당자 편집이 정본이고 시스템이
  덮어쓰지 않는다. 완전 자동 발송 없음 — 공문은 사람이 책임지는 문서다.
- **LLM 서술 없음 (v1)** — 사고 시점의 즉시성이 우선. 데이터 기반 템플릿
  이면 초안으로 충분하다.
- 저장은 `tb_report` 에 얹지 않는다 — 그 테이블은 항목 리스트 구조고
  상황보고는 서술 섹션 문서다. 재사용 포인트는 저장이 아니라
  **브라우저 인쇄·편집→확정 흐름**이다 (로드맵 부록 A.3 정정 반영).
- **"영향 세대수"는 자동 채움하지 않는다** — 세대·급수인구 데이터가 DB 에
  없다 (2026-07-28 조사). impact 섹션에 담당자가 기입.

## 2. 데이터 모델 — `tb_incident_report` (0133)

차수(1보/2보…)는 `parent_id` 자기참조 체인. 섹션은 jsonb
(overview/situation/actions/impact/outlook/contact).

## 3. 자동 채움

| 항목 | 소스 |
|---|---|
| 발생 시각 | 지정값 → 없으면 그 시설 최근 24h 첫 경보 → 없으면 now |
| 상황·경과 | 발생 −60분(전조)부터의 경보 — **(메시지) 접기** (반복 N회, 잠식 방지 원칙) |
| 조치 사항 | `tb_task_master` 같은 구간 |
| 향후 계획 | 진행중 경보 수 + 기재 요망 문구 |
| 개요 | **비움** — 사고 서술은 시스템이 추정하지 않는다 |

**후속보(2보~)는 직전 보 작성 시점 이후 구간만** 수집한다 — 같은 내용
반복 방지. 개요·영향·연락처는 직전 보에서 이월.

## 4. 보호 규칙 (전부 실검증)

- 확정(final) 후 수정 불가 · 후속보가 달린 보고 삭제 불가 · 초안만 삭제 가능
- 제목은 담당자가 자유 편집 (같은 사고라도 부서마다 제목이 다르다)

## 5. API

`POST /incident/draft` (1보=sitename / 후속보=parent_id) ·
`GET /incident` · `GET/PATCH/DELETE /incident/{id}`
(`slm/endpoints/incident_report.py`)

## 6. 후속 (P2)

- `report_summarizer` 재사용한 AI 서술 다듬기 (편집 보존 전제)
- 알람 상세·작업에서 "1보 작성" 진입 버튼
- 세대·급수인구 데이터가 반입되면 영향 범위 자동 채움
