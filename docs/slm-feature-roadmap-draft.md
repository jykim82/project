## 3. 항목별 상세

### 3.A 제한적 에이전트 루프

현재 구조는 백엔드 계산 결과를 LLM이 서술하는 단방향 방식. 이를 **LLM이 화이트리스트된 도구를 호출해 근거를 수집하는 루프**로 확장.

- **불변 원칙:** LLM은 여전히 독립 추론하지 않는다. 도구 호출 결과의 서술만 담당.
- **도구 화이트리스트 예시**
  - 과거 동일 시간대·동일 센서 이력 조회
  - 인접 블록 유량/압력 대조 조회
  - 관련 지식 카드 검색 (§3.B 연동)
  - 최근 조치 이력 조회
- **권한 게이트:** 조회 계열 도구는 자동 실행. 제어·설정 변경 계열은 운영자 승인 필수. (모드 구분 필요)
- **루프 제한:** 최대 호출 횟수·타임아웃 상한 필수. 폐쇄망 로컬 LLM 환경이므로 응답 지연이 곧 사용성 저하.

**미결정:** 도구 호출 결정을 로컬 LLM에 맡길지, 룰 기반 라우터가 도구를 선택하고 LLM은 서술만 할지.

---

### 3.B 현장별 지식 UI 등록

운영자의 암묵지("이 지점은 매주 화요일 역세척으로 유량이 튄다")를 코드 수정 없이 시스템에 반영.

**등록 방식: 파일 편집이 아닌 웹 UI 입력·등록으로 확정.**
사유: 폐쇄망 환경에서 담당자의 서버 직접 접근은 비현실적. 공공 납품 특성상 등록·수정 이력의 감사 추적 필요.

#### 구조: "지식 카드" 단위

단일 대형 텍스트가 아닌 카드 단위로 분할한다. 상황 발생 시 관련 카드만 선택해 컨텍스트에 주입 → 지점 수 증가 시에도 토큰 증가가 선형으로 통제되고, 무관한 지점 지식 혼입으로 인한 오답을 방지.

#### 등록 폼 필드 (제안)

| 필드 | 설명 |
|------|------|
| 유형 | 주기 이벤트 / 설비 특성 / 예외 상황 / 조치 절차 / 연락 체계 |
| 적용 대상 | 지점·블록·센서 태그 (다중 선택) |
| 조건 | 요일·시간대·계절·임계 조건 (구조화 입력) |
| 서술 | 자유 텍스트 (LLM 서술용 + pgvector 임베딩 대상) |
| 유효기간 | 상시 / 기간 한정 (공사 기간 등) |
| 상태 | 초안 → 승인 → 적용 |
| 이력 | 작성자, 수정자, 변경 이력 |

#### 데이터 모델 초안 (제안, 확정 아님)

```
site_knowledge
  id                uuid
  type              enum
  target_refs       jsonb    -- 지점/블록/센서 태그 배열
  conditions        jsonb    -- 구조화된 조건 (룰 엔진이 파싱)
  description       text     -- 자유 서술
  embedding         vector   -- pgvector
  valid_from        timestamptz
  valid_until       timestamptz null
  status            enum
  created_by        text
  created_at        timestamptz

site_knowledge_revision   -- 변경 이력 (감사 추적)
```

#### 핵심 설계 요구사항

**지식을 LLM 프롬프트 전용으로 두지 않는다.** 구조화된 `conditions`는 이상감지 룰 엔진이 직접 참조해야 한다.

- 예: "매주 화 09~11시 역세척" → 해당 시간대 유량 스파이크는 알람 억제 또는 신뢰도 가중치 하향
- 이를 통해 §3.C(오탐 피드백)와 연결: 오탐 라벨이 축적되면 시스템이 지식 카드 등록을 선제 제안하는 흐름 가능

#### 안전장치 (필수)

1. **등록 전 영향 미리보기** — "이 카드 적용 시 지난 30일 알람 127건 중 14건 억제" + 억제 대상 목록 표시. 잘못 등록된 지식으로 실제 사고를 놓치는 것이 이 기능의 주요 리스크이며, 미리보기로 대부분 차단 가능.
2. **억제 로그 분리 보관** — 억제된 알람도 삭제하지 않고 별도 뷰에 보존. 감사 시 "왜 이 알람이 발생하지 않았는가"에 답할 수 있어야 함.

#### 승인 워크플로

2단계 승인(초안→승인)은 **설정으로 on/off 가능하게** 구성. 지자체 현장은 담당자가 1~2명인 경우가 많아 강제 승인 단계가 오히려 병목이 될 수 있음.

---

### 3.C 오탐 피드백 루프

이상감지 결과 화면에서 운영자가 **실제 / 오탐 / 점검필요** 중 하나를 1클릭 라벨링.

- 수집된 라벨로 룰 가중치·임계값 조정
- **부수 효과(중요):** "도입 6개월 후 오탐률 42% → 11%" 형태의 정량 실적 확보 → 나라장터 제안서 및 후속 사업 근거로 활용
- 오탐률 추이 대시보드 필요
- §3.B와 연동: 반복 오탐 패턴 → 지식 카드 등록 제안

---

### 3.D 상황보고서 자동 초안

기존 일일보고 3종 출력(HTML+print CSS / Playwright PDF / openpyxl Excel) 구조를 재사용.

- 사고 발생 시 **1보/2보 공문 초안** 자동 생성
- 자동 채움 항목: 발생 시각, 영향 세대 수, 관련 지점, 조치 이력, 현재 상태
- 담당자가 편집 후 확정하는 흐름 (완전 자동 발송 아님)
- 실무 부담이 가장 큰 업무 영역이라 체감 효과가 즉각적

---

### 3.E 현장 점검 모바일

PLC 고장 진단용으로 구축한 OCR 파이프라인(OpenCV / EasyOCR / PaddleOCR)을 재활용.

- 현장에서 계기판 촬영 → 수치 자동 추출·입력
- **오프라인 우선** 설계 (현장 통신 환경 불안정 가정), 복귀 후 동기화
- 신규 개발이 아닌 기존 자산의 2차 활용이므로 투입 대비 효과 양호

## 4. 미결정 사항

- [ ] A: 도구 선택 주체 (로컬 LLM vs 룰 기반 라우터)
- [ ] B: 지식 카드와 기존 룰이 충돌할 때의 우선순위 정책
- [ ] B: 지식 카드 유형(enum) 최종 확정
- [ ] C: 라벨 축적량이 적을 때(초기 도입 3개월 이내)의 가중치 조정 정책
- [ ] E: 모바일 구현 방식 (PWA vs 네이티브)
- [ ] 전체: 항목 간 구현 순서 및 릴리스 묶음

## 5. 유지해야 할 설계 원칙

이 로드맵의 어떤 항목도 아래 원칙을 침해하지 않는다.

1. **LLM as announcer** — LLM은 사전 계산된 백엔드 데이터로부터 한국어 서술을 생성한다. 독립적으로 추론하거나 판단하지 않는다.
2. **이상 감지는 룰 엔진 + 통계 모델이 담당**하며 LLM 추론에 의존하지 않는다.
3. **폐쇄망(air-gapped) 호환** — 외부 의존성 없이 동작해야 한다.
4. **감사 추적 가능성** — 공공 부문 납품 특성상 모든 자동 판단은 사후에 근거를 설명할 수 있어야 한다.

## 부록 A — 기존 구현과의 대조 (2026-07-27 편입 시 확인)

> 본문(§0~§5)은 원안 그대로 보존한다. 아래는 문서를 레포에 편입하면서
> 현재 코드베이스와 대조한 결과다. **원안의 전제 중 사실과 다른 것 3건**이
> 있어, 구현 착수 전에 재검토가 필요하다.

### A.1 §2 "What-if 시뮬레이션 UI — 제외" — **이미 구현되어 있음**

원안은 "지도에서 밸브 조작 시 단수 영향·압력 저하 예측"을 검토 범위에서
제외했으나, 이 기능은 **B1 EPANET SKU 로 이미 출시 상태**다.

| 메뉴 | 라우트 |
|---|---|
| 차단밸브 영향범위 | `/crisis/valve-impact` |
| 관로 파손 시뮬 | `/crisis/pipe-break` |
| 펌프 가동 변경 | `/crisis/pump-control` |
| 시나리오 비교 | `/crisis/scenario-diff` |

사양: `docs/epanet-menu-spec.md`, `docs/gis_plan.md`(Phase 1 완료),
`docs/feature-sku-spec.md`(B1). 따라서 §2 는 "제외"가 아니라 **"기 구현 —
고도화 여부만 판단"** 으로 다뤄야 한다.

### A.2 §3.E "PLC 진단용 OCR 파이프라인(OpenCV/EasyOCR/PaddleOCR) 재활용"
— **그런 파이프라인은 없음**

현재 비전 처리는 **Ollama `gemma4` 멀티모달** 단일 경로다
(`slm/vision_agent.py`, `docs/chat-photo-upload-scenario-spec.md`).
EasyOCR·PaddleOCR 는 의존성에 없고, `cv2` 는 다른 패키지가 끌고 온 것이라
우리 코드가 쓰지 않는다.

즉 §3.E 는 "기존 자산의 2차 활용"이 아니라 **신규 OCR 스택 도입**이 된다.
투입 대비 효과 판단이 원안과 달라지므로 우선순위 재산정 필요.
(대안: 계기판 수치 추출도 gemma4 비전으로 처리 — 신규 스택 없이 검증 가능)

또한 현장 점검 모바일 자체는 **`/field` 현장 모드로 이미 존재**한다
(`docs/field-mode-spec.md` v3 — 알람 대응·시설 점검·조치 완료·자유 입력).
§3.E 는 신규 기능이 아니라 **현장 모드에 계기판 촬영 입력을 더하는 확장**
으로 잡는 것이 맞다. "오프라인 우선 + 복귀 후 동기화"는 현장 모드에 없는
새 요구사항이라 이 부분이 실질 신규분이다.

### A.3 §3.D "일일보고 3종 출력(HTML+print CSS / Playwright PDF / openpyxl Excel)"
— PDF 는 Playwright 가 아니라 **브라우저 인쇄**

`docs/report-spec.md` §5.5 기준 PDF 는 self-contained HTML + 인쇄 CSS 를
새 창으로 띄워 브라우저가 출력한다. 서버 측 PDF 생성(puppeteer)은 후속
항목으로 남아 있다. 폐쇄망에서 헤드리스 브라우저를 새로 반입하는 비용이
있으므로, 1보/2보 공문도 **기존 인쇄 경로 재사용**이 기본이다.

### A.4 §3.C 오탐 피드백 — **기반 데이터는 이미 쌓이는 중**

`tb_equipment_alarm_report.is_false_alarm` 로 오경보 라벨이 이미 수집되고
있다 (2026-07-27 기준 Y 1,457건 / N 17,997건). API·UI 도 있다
(`PUT /crisis/alarm-reports/false-alarm`, `markFalseAlarm`).

따라서 §3.C 의 실질 신규분은 세 가지다.
1. 2분법(Y/N) → **3분법(실제/오탐/점검필요)** 확장
2. **오탐률 추이 대시보드** (영업 근거 자료의 본체)
3. 라벨 → 룰 가중치 반영 경로

주의: 채팅 오답 피드백(`docs/chat-feedback-telemetry-spec.md`,
`memory/feedback_wrong_answer_loop.md`)과 **다른 체계**다. 하나로 합치지
말 것 — 전자는 인텐트 분류 품질, 후자는 이상감지 판정 품질이다.

### A.5 §3.B 지식 카드의 알람 억제 — 기존 억제 체계와 정합 필요

이미 두 가지 억제 경로가 있다.
- **작업관리 억제** — `tb_task_master.suspend_alarm_types` (운영자가 작업
  등록 시 명시 지정)
- **태그 품질 계층** — `tb_tag_quality` 기반 알람 완화
  (`docs/tag-quality-layer-spec.md` P3)

지식 카드가 세 번째 억제 경로가 되면 "이 알람이 왜 안 울렸는가"의 답이
셋으로 갈린다. §3.B 의 "억제 로그 분리 보관"은 **세 경로를 하나의 억제
로그로 통합**하는 형태여야 감사 추적이 성립한다.

또한 `memory/feedback_no_auto_alarm_link.md` — **장애 기록으로 알람을
자동 해제하지 않는다**는 기존 원칙과 충돌하지 않는지 확인할 것. 지식 카드는
"등록된 조건에 한해, 사전에 명시적으로" 억제하는 것이라 원칙과 양립하지만,
자동 제안(§3.C 연동)이 자동 적용으로 넘어가면 원칙 위반이다.

### A.6 반복 경보와의 관계 (2026-07-27 신규)

`docs/alarm-chattering-spec.md` 가 §3.C 와 인접하다. 반복 경보 순위표는
"어떤 경보가 목록을 잠식하는가"를 이미 사실 집계로 보여준다 — 오탐 라벨이
붙기 전에도 조치 대상을 뽑을 수 있다. §3.C 착수 시 **채터링 상위 항목을
라벨링 우선 대상으로 노출**하면 초기 라벨 축적 속도를 올릴 수 있다
(§4 미결정 항목 "라벨 축적량이 적을 때의 정책"에 대한 답 후보).

### A.7 우선순위에 대한 의견

원안은 C 를 1순위로 봤고, 근거(영업 효과)에 동의한다. 다만 A.4 대로 C 의
기반이 이미 있으므로 **투입은 원안 추정보다 작다**. 반대로 E 는 A.2 대로
신규 스택 도입이라 **원안 추정보다 크다**. 순서 재산정 시 이 두 가지를
반영할 것.

## 부록 B — 미결정 사항(§4)에 대한 권고안 (2026-07-28)

> 결정이 아니라 **권고**다. 항목 착수 시점에 이 권고를 출발점으로 확정한다.

### B.1 A: 도구 선택 주체 → **룰 기반 라우터 권고**

LLM 이 도구를 고르게 하면 §5.1(LLM as announcer)이 흔들리고, 로컬 LLM 의
도구 선택은 지연·비결정성을 더한다. 이미 인텐트 아키텍처
(`intent-architecture-spec`)가 룰 기반 분류 → 핸들러 구조다 — 도구 화이트
리스트를 인텐트 파이프라인의 연장으로 두고, LLM 은 수집된 근거의 서술만
맡기는 것이 기존 구조와 정합한다.

### B.2 B: 지식 카드 ↔ 기존 룰 충돌 → **안전 신호 불가침**

우선순위: **SCADA 임계(HH/LL) · 태그 품질 게이트 > 지식 카드**.
카드가 할 수 있는 것은 통계 감시(z-score·IForest)의 신뢰도 하향과 억제
마킹까지다. 안전 임계 알람은 카드로 끌 수 없다 — 잘못 등록된 지식이
실제 사고를 가리는 최악 경로를 구조적으로 차단한다.

### B.3 B: 지식 카드 유형 → **4종 권고 (연락 체계 제외)**

주기 이벤트 / 설비 특성 / 예외 상황 / 조치 절차.
원안의 '연락 체계'는 기존 비상연락처(`emergency-contact-spec`)와 중복 —
같은 정보의 정본이 둘이 되면 안 된다.

### B.4 C: 라벨 초기 축적기 → **가중치 조정 유보 + 우선 노출**

카테고리별 라벨 30건 미만이면 자동 가중치 조정을 하지 않는다 (소표본
과적합). 그동안은 ① 라벨 수집·표시만 ② **채터링 순위 상위를 라벨링 우선
대상으로 노출**해 축적을 가속한다 (부록 A.6 — 반복 경보 순위표 재사용).

### B.5 E: 모바일 구현 방식 → **PWA 권고**

폐쇄망 고객에 앱스토어 배포 경로가 없다. 기존 `/field` 가 이미 모바일
웹이므로 PWA(오프라인 캐시 + 홈 화면 설치)가 유일하게 현실적인 경로다.

### B.6 구현 순서 → **C → D → B → A → E 권고**

- **C 먼저**: 기반(`is_false_alarm` 수집)이 이미 있어 투입 최소 + 영업
  실적(오탐률 추이) 확보가 가장 급하다 (부록 A.4·A.7)
- **D**: 기존 보고서 3종 출력 재사용 — 독립적이라 병행 가능
- **B**: C 의 라벨이 쌓여야 "카드 등록 선제 제안"(§3.B↔C 연동)이 성립
- **A**: B 의 지식 카드 검색이 핵심 도구라 B 이후가 자연스럽다
- **E 마지막**: OCR 신규 스택 도입이라 원안 추정보다 투입이 크다 (부록 A.2)
