# 반복 경보(채터링) 정리 사양 v1

경보 목록을 잠식하는 반복 경보를 **접어서 보여주고**, 조치 대상을 순위표로
뽑아준다.

**관련**: `docs/fault-category-policy.md`(분류 정책),
`docs/alarm-category-summary-spec.md`(분류별 현황),
`memory/feedback_no_photo_per_alarm.md`

---

## 1. 왜 하는가 — 실측

2026-07-27 운영 DB 조사:

| 지표 | 값 |
|---|---|
| 최근 30일 전체 경보 | 3,553건 |
| 그중 **반복 경보**(같은 현장·메시지 10회 이상) | 3,411건 (96%) |
| 그중 **채터링**(짧게 붙었다 떨어지는 것) | 5건이 **3,099회 = 전체의 87.2%** |
| 최다 단일 경보 — 죽동(배) 탁도계 통신이상 | **2,866건 (전체의 80.7%)**, 평균 7.3분, 재발간격 중앙값 3분 |
| 최근 90일 경보 확인율 | 12,053건 중 36건 = **0.3%** |

**한 태그가 전체 경보의 80%를 만들고, 그래서 운영자가 경보를 안 본다.**
확인율 0.3% 는 기능이 부족해서가 아니라 목록이 신뢰를 잃었다는 뜻이다.
경보 기능을 더 얹기 전에 이걸 먼저 걷어내야 한다.

## 2. 설계 원칙

### 2.1 원본을 지우거나 합치지 않는다
경보 이력은 감사 자료다. 집계는 **표시 계층에서만** 한다.
DB 행은 그대로 남고, 목록이 접힐 뿐이며, 펼치면 개별 건이 전부 보인다.

### 2.2 "억제"와 구분한다
이미 있는 두 가지 억제와 **혼동하면 안 된다**.

| 개념 | 의미 | 주체 |
|---|---|---|
| 작업 억제 (`task_suppressed`) | "작업 중이니 이 경보는 무시" | 운영자의 정책 결정 |
| 오경보 (`is_false_alarm`) | "이건 잘못 울린 것" | Node-RED 필터 / 운영자 판정 |
| **반복 접기** (본 사양) | "같은 경보가 N번 울렸다" | 사실 보고 — 판단 없음 |

반복 접기는 억제 여부와 **무관하게** 집계한다. 억제된 경보도 반복 횟수는
센다 — 억제는 표시 여부의 문제고, 반복은 현상의 크기다.

### 2.3 채터링과 만성을 가른다 — 조치 주체가 다르다

| 유형 | 성질 | 조치 |
|---|---|---|
| **채터링** | 짧게 붙었다 떨어지는 반복 | SCADA 데드밴드·on-delay 설정, 현장 계측기 점검 |
| **만성** | 상태가 오래 유지되며 반복 | 공급·설비 검토. **경보 설정을 건드리면 위험을 가린다** |

판정은 **평균 지속시간 하나**로 한다 (`_CHATTERING_MAX_DURATION_MIN = 15분`).

> **처음 기준은 틀렸다.** "시간당 발생 횟수 ≥ 0.5" 를 함께 걸었더니 실측에서
> 두 건이 오분류됐다.
> - 성하리(배) 오뚜기 HH — 재발간격 중앙값 **1.0분**인데 관측구간이 길어
>   0.32회/시간 → '만성'으로 빠짐. 간격 1분이면 명백한 채터링이다.
> - 천의리(가) 가압장침수 — **1.5분짜리 펄스가 135회**인데 0.19회/시간 →
>   역시 '만성'. 실제 침수가 아니라 순간 펄스다.
>
> 시간당 횟수는 관측 구간 전체의 평균이라 "몰려서 터지는" 성질을 못 잡는다.
> 반면 지속시간은 "상태가 실제로 유지됐는가"를 직접 말해준다.
> 시간당 횟수·재발 간격은 판정에서 빼고 **강도 지표**로만 표시한다.

### 2.4 묶음 키는 `(sitename, alarm_msg)`
`tagsn` 이 아니다. 태그 교체·재등록으로 tagsn 이 바뀌어도 운영자에겐 같은
경보다. `tagsn` 은 대표값으로 함께 돌려준다 (SCADA 에서 찾아갈 때 필요).

## 3. 백엔드

### 3.1 `GET /crisis/alarm-chattering` (신규)
`slm/endpoints/alarm_chattering.py` — `alarm_crisis.py` 가 이미 900줄을 넘어
별도 모듈로 분리.

**파라미터**: `days`(1~365, 기본 30), `min_count`(2~1000, 기본 5)

**응답**
```jsonc
{
  "status": "OK",
  "days": 30, "min_count": 10,
  "total_alarms": 3553,      // 기간 내 전체 경보
  "repeat_alarms": 3411,     // 그중 반복에 해당하는 건수 — "잠식의 크기"
  "thresholds": { "chattering_max_duration_min": 15.0 },
  "items": [{
    "sitename", "facilitytype", "equipmenttype", "tagsn",
    "alarm_msg", "alarm_category", "alarm_severity",
    "count", "share_pct",              // 전체 대비 비중
    "confirmed", "confirm_rate",       // 확인율 — 무시되고 있는지
    "first_seen", "last_seen",
    "avg_duration_min",                // 판정 기준
    "median_gap_min",                  // 강도(재발 촘촘함). 평균 아닌 중앙값
    "per_hour",                        // 강도(관측구간 기준 빈도)
    "kind": "chattering" | "chronic"
  }]
}
```

**재발간격에 중앙값을 쓰는 이유**: 야간 정지 등으로 한 번씩 크게 벌어지는
구간이 평균을 끌어올려 채터링을 가려버린다.

**시간당 횟수를 관측구간(첫~마지막) 기준으로 계산하는 이유**: 하루 몰아친 뒤
멎은 경보를 30일로 나눠 희석하지 않기 위함.

### 3.2 `GET /crisis/alarm-reports` — `repeat_count` 추가
```sql
COUNT(*) OVER (PARTITION BY sitename, alarm_msg) AS repeat_count
```
윈도 함수는 `LIMIT` 이전에 계산되므로 잘린 500행이 아니라 **필터 전체 기준**
이다. 목록 접기에 쓴다.

### 3.3 비용
집계 SQL 한 번. 인덱스는 기존 `idx_alarm_report_start_time` 으로 충분하다.
신규 테이블·배치·모델 없음 — 저사양 서버 전제에 맞춘 선택.

## 4. 프런트 (P1)

### 4.1 목록 접기 — `AlarmReportTable`
`repeat_count >= _FOLD_MIN` 인 그룹은 **가장 최근 1건만** 표시하고
`반복 N회` 배지를 단다. 배지 클릭 시 그 그룹만 펼친다.

- 접기 기준은 **화면 상태**다. 필터·정렬을 바꾸면 다시 계산된다.
- 작업 억제(`억제중`)·오경보 배지와 **색·모양을 다르게** 한다 (§2.2).
- 진행중 목록에서는 접지 않는다 — 대응해야 할 건은 개별로 보여야 한다.

### 4.2 반복 경보 탭 — `/crisis/alarm-dashboard`
기존 `dashboard` / `history` 탭에 **`repeat`(반복 경보)** 추가.
신규 메뉴를 만들지 않는다 — 운영자가 경보를 보는 자리에 두는 게 맞고,
메뉴 증식은 구축 동선을 흐린다.

구성:
- 상단 요약 — "최근 30일 경보 3,553건 중 **반복 3,411건(96%)**,
  채터링 5건이 3,099회(87.2%)"
- 순위표 — 유형 배지 / 현장 / 경보 / 횟수·비중 / 평균 지속 / 재발 간격 / 확인율
- 행 클릭 → 해당 `(sitename, alarm_msg)` 로 필터된 이력 탭으로 이동
- 유형 필터 (전체 / 채터링 / 만성), 기간 선택 (7일 / 30일 / 90일)

### 4.3 표시 문구
"억제"라는 말을 쓰지 않는다 (§2.2). `반복 N회`, `채터링`, `만성` 을 쓴다.

## 5. 이 사양이 하지 않는 것

- **자동 억제·자동 해제 없음.** 반복이 많다고 시스템이 경보를 끄지 않는다.
  끄는 판단은 운영자 몫이고, 그 경로는 이미 작업관리 억제에 있다.
  (`memory/feedback_no_auto_alarm_link.md` 와 같은 계열 — 자동 연계 금지)
- **SCADA 설정 변경 없음.** 데드밴드·on-delay 는 제품 밖(현장 SCADA) 조치다.
  본 화면은 **대상을 식별해 넘겨주는 것**까지 한다
  (`docs/alarm-threshold-coverage.md` 와 같은 성격).
- 임계 신설 제안 없음 — 별도 사양 소관.

## 6. 후속 (P2 이후)

- 반복 경보를 **점검 후보로 전달** — 태그 품질 계층(`tb_tag_quality`)의
  점검 후보와 합류. 죽동 탁도계처럼 지속 재발하는 계측기는 교체 후보다.
- 교대 인수인계 브리핑(A-2)에서 "이번 근무 중 반복 경보 상위 3건" 표시.
- 채터링 판정 임계(15분)의 현장별 조정 — 지금은 전역 상수. 필요해지면
  `SITE_SETTING` 으로 뺀다 (하드코딩 회피 경로 확보).
