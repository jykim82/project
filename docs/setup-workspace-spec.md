## 1. 배경 — 왜 통합인가

구축 담당자(SI 엔지니어)의 실제 작업은 **하나의 시설을 세로로 관통**한다.

```
시설 등록 → 설비 등록 → 태그 매핑 → 통신 정보 → 계통도 연결 → 검수
```

그런데 현재는 이 한 흐름이 화면 5개에 흩어져 있다. 화면을 옮길 때마다
"방금 만든 그 시설"을 다시 검색해서 찾아야 한다 — **컨텍스트가 화면 경계에서
끊긴다.** 이것이 구축이 오래 걸리는 진짜 이유다.

### 1.1 하지 말아야 할 통합
**용수 계통도와 통신망을 한 캔버스에 겹치는 것은 채택하지 않는다.**

| | 용수 계통 | 통신망 |
|---|---|---|
| 노드 | 시설 99 (배수지·가압장·감압·블록) | 장비 295 (PLC·RTU·모뎀·펌프…) |
| 엣지 | 상하류(물 흐름) 97 | 통신 링크(프로토콜·포트) 280 |
| 판정 | 순환·고아·EPANET 정합 | 미연결·IP 중복·겹침 |

노드 집합도 엣지 의미도 다르다. 한 화면에 겹치면 394 노드에 두 종류 엣지가
교차해 판독이 불가능해지고, 두 lint 의 의미도 섞인다.

### 1.2 실제로 통합되는 것
네 축은 별개 축이 아니라 **같은 트리의 깊이**다.

```
시설 (sitename + facilitytype)          ← tb_flow_diagram_node 가 이 키로 물림
 └ 설비 (equipment_id)                  ← tb_network_info 가 이 키로 물림
    ├ 태그 (tagsn) → 트렌드
    └ 통신 (ip/protocol) → 통신 링크
```

따라서 통합 대상은 캔버스가 아니라 **① 좌측 트리(공통 탐색) ② 우측 인스펙터
(공통 편집) ③ 한 시설을 끝까지 끌고 가는 등록 흐름**이다.

## 2. 화면 구조

`/setup/workspace` — 3 분할 고정 레이아웃.

```
┌──────────────────────────────────────────────────────────────────────┐
│ 툴바:  [레이어: 용수 계통 | 통신망]  [추가▾] [수정] [삭제] [자동정렬]  lint  │
├────────────┬────────────────────────────────────────┬────────────────┤
│ 트리        │ 캔버스 (레이어에 따라 교체)               │ 인스펙터        │
│ 시설 99     │                                        │ 정보           │
│ └ 설비      │  용수 계통 = CanvasEditor               │ 설비           │
│    └ 태그   │  통신망   = NetworkLinkEditor           │ 태그·트렌드     │
│            │                                        │ 통신           │
│ [검색]      │                                        │ 인과           │
└────────────┴────────────────────────────────────────┴────────────────┘
```

### 2.1 좌측 트리 (신규)
- 시설 → 설비 → 태그 3단. 검색어 입력 시 3단 전체를 관통 검색
- 선택 시 **캔버스의 해당 노드로 이동·하이라이트 + 인스펙터 동기화**
- 배지: 미등록(기초정보 공백)·태그 미매핑·통신 미등록 — [setup-audit](setup-audit-spec.md) 검사 결과 재사용
- 레이어를 통신망으로 바꿔도 **선택은 유지**된다 (시설 선택 → 그 시설의 장비들로 포커스)

### 2.2 캔버스 레이어 토글
- 기존 두 에디터를 **그대로 레이어로 흡수**한다 (재작성 금지 — 각 에디터의
  lint·자동 정렬·CRUD 툴바는 이미 완성돼 있다)
- 툴바는 레이어에 따라 교체. 공통 슬롯(추가/수정/삭제/자동정렬/lint)만 유지
- 레이어 전환 시 뷰포트는 각각 기억 (전환할 때마다 fitView 하면 방향 감각 상실)

### 2.3 우측 인스펙터 (공통화)
현재 계통도 캔버스의 속성 패널(정보/설비/트렌드/인과)에 **통신 탭을 추가**하고,
통신망 레이어에서도 같은 인스펙터를 쓴다.

| 탭 | 대상 | 정본 | 현황 |
|----|------|------|------|
| 정보 | 시설 | `tb_service_*_info` / `tb_block_info` | 편집 O, **신규 등록 X** → §3 |
| 설비 | 설비 | `tb_equipment_info` | CRUD O |
| 태그·트렌드 | 태그 매핑 / 트렌드 | `tb_equipment_tag_map` / `tb_trend_catalog` | CRUD O |
| **통신** | 통신 정보·링크 | `tb_network_info` / `tb_network_link` | **신규** — 기존 폼 재사용 |
| 인과 | 인과 체인 | `tb_causal_chain_override` | O |

## 3. 시설 등록 마법사 (통합의 핵심)

현재 캔버스에서 시설을 드롭하면 `신규배수지_1` 같은 **임시 노드**만 생기고,
정식 등록은 시설정보 구축 화면에서 따로 해야 한다. 이 단절이 남아 있는 한
"캔버스에서 구축한다"는 말이 성립하지 않는다.

**드롭 → 4단계 마법사(우측 인스펙터에서 진행):**

| 단계 | 내용 | 저장 |
|------|------|------|
| ① 시설 | 유형·현장명·주소·제원 | `POST /facility/*` (기존 폼 재사용) |
| ② 설비 | 설비 추가 (유형·제조사·설치일) | `POST /equipments` |
| ③ 태그 | 설비↔태그 매핑 (미매핑 태그 추천) | `POST /canvas/equipment-tag-link` |
| ④ 통신 | IP·프로토콜·상위 장비 링크 | `POST /network/infos`, `/network/links` |

- 각 단계는 **건너뛸 수 있고**, 건너뛴 항목은 트리 배지 + 구축 검수에 그대로 남는다
- ① 완료 시점에 임시 노드가 정식 노드로 승격되고 상하류 연결이 가능해진다
- 마법사 종료 후에도 인스펙터 탭으로 언제든 이어서 채울 수 있다 (같은 폼)

## 4. 유지 원칙 (통합해도 바꾸지 않는 것)

1. **표 화면은 남긴다.** 295개 장비·1천 단위 태그의 대량 편집·CSV 일괄은 표가
   압도적으로 낫다. 워크스페이스는 "한 시설을 끝까지", 표는 "여러 건을 한 번에".
   각 통합 페이지의 목록 탭을 그대로 유지한다.
2. **정본 이원화 금지.** 워크스페이스는 기존 API·기존 폼을 재사용만 한다.
   새 저장 경로를 만들지 않는다.
3. **검수 진입점은 `/setup/audit` 하나.** 워크스페이스는 검수 결과를 배지로
   비출 뿐, 판정 로직을 복제하지 않는다.
4. **폐쇄망·region 멀티테넌시** 기존 제약 그대로.

## 5. 선결 과제 — 좌표 정본 이원화

현재 캔버스 좌표 정본이 둘이다.

| 레이어 | 좌표 저장 | 결정 경위 |
|--------|-----------|-----------|
| 용수 계통 | `tb_flow_diagram_node.x/y` (경위도 사상) | canvas-editor-unification-spec P1 |
| 통신망 | `tb_network_info.meta.canvas_pos` (px) | network-link-editor-spec §2.2 |

워크스페이스에서 두 레이어가 한 툴바("자동 정렬")를 공유하므로 **저장 경로를
통일할지 먼저 정해야 한다.** 통신망 쪽 `meta.canvas_pos` 는 [E-054] — 배치
저장이 장비 대장 행을 만들어 대장이 늘어나는 부수효과 — 의 원인이기도 하다.

**권고: 레이아웃 전용 테이블 `tb_canvas_layout(region, layer, node_key, x, y)`
로 통일.** 표시 좌표가 자산 대장(`tb_network_info`)·계통도 정본
(`tb_flow_diagram_node`) 어느 쪽도 오염시키지 않는다. 마이그레이션은 기존 두
경로의 값을 그대로 옮기면 되고, 읽기는 LEFT JOIN 한 번이다.

> 이 결정은 P2 착수 전 확정 필요. 확정 전에는 각 레이어가 현재 경로를 유지하고,
> 워크스페이스는 저장 호출만 위임한다(동작에는 영향 없음).
