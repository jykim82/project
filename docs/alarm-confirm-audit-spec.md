# 경보 확인 책임 추적 사양 v1

경보 확인에 **누가·언제**를 기록한다. 지금까지는 `alarm_confirm_yn='Y'`
하나뿐이라 감사 질문("이 경보를 누가 인지했는가")에 답할 수 없었다.

**관련**: `docs/alarm-chattering-spec.md`(확인율 0.3% 문제의 다른 반쪽),
`docs/shift-handover-spec.md`(교대 간 책임 인계)

---

## 1. 왜 하는가

- **감사 추적** — 공공 납품에서 "이 경보가 인지됐는가, 누가, 언제"는 사고
  조사의 첫 질문이다. Y/N 플래그로는 답할 수 없다.
- **교대 환경** — 3교대에서 확인 주체가 기록되지 않으면 책임이 근무자 간에
  증발한다.
- **확인율 개선의 전제** — 90일 12,053건 중 확인 36건(0.3%). 책임이
  기록되지 않는 행동은 하지 않게 된다. 기록은 개선의 시작점이다.

## 2. 데이터 모델 — Migration 0131

`tb_equipment_alarm_report` 에 두 컬럼 추가:

| 컬럼 | 의미 |
|---|---|
| `confirmed_by` varchar(50) | 확인자 user_id. NULL = 기록 도입 전 확인 건 |
| `confirmed_at` timestamptz | 확인 시각 (`info_updated` 와 달리 확인 행위만) |

**기존 확인 건은 NULL 로 남긴다.** 과거 확인자의 소급 추정은 하지 않는다 —
감사 컬럼에 추정값이 들어가는 순간 컬럼 전체를 못 믿게 된다.

## 3. 기록 규칙

**최초 확인만 기록한다.** 재확인 클릭·다른 사용자의 재확인이 기록을 덮으면
감사가 무의미하다.

```sql
confirmed_by = CASE WHEN confirmed_by IS NULL AND %s <> ''
                    THEN %s ELSE confirmed_by END,
confirmed_at = COALESCE(confirmed_at, NOW())
```

기록 지점 (셋 다 같은 규칙):
1. `PUT /crisis/alarm-reports/confirm` — 개별·전체 확인 버튼
2. `POST /crisis/alarm-reports/resolve` — 비전 점검 해제. **해제도 확인의
   한 형태**이므로 함께 기록
3. `user_id` 는 클라이언트 세션(`session.user.user_id`)에서 전달 — 이
   코드베이스의 기존 패턴(schedule·memo 와 동일). 빈 값이면 `confirm_yn`
   만 갱신하고 확인자는 비워둔다 (엉뚱한 값보다 빈 값이 낫다)

## 4. 표시

경보 목록 확인 컬럼: 체크 아이콘 아래 확인자 id, 툴팁에
`jykim 확인 · 2026-07-28 14:20:48`. 기록 없는 과거 건은
"확인됨 (확인자 기록 도입 전 건)" 툴팁만.

## 5. 하지 않는 것

- **자동 확인 없음** — 알람 자동해제 루프(`_release_stale_alarms`)는
  `alarm_status` 만 바꾸고 확인 기록을 만들지 않는다. 시스템이 해제한 것과
  사람이 인지한 것은 다른 사실이다.
- 확인 취소 기능 없음 (v1) — 감사 기록은 취소가 아니라 정정 이력이 필요한
  영역이라, 요구가 생기면 별도 설계.

## 6. 후속 (P2)

- **미확인 에스컬레이션 상신** — N분 미확인 시 메신저·비상연락처로 단계
  상신 (폐쇄망이라 SMS 대신 기존 메신저 재사용). 표시 계층의 에스컬레이션
  (미조치 경과 타이머)은 이미 있음 — 상신은 별도 결정 필요
- 확인율 추이 통계 (confirmed_at 기반) — 반복 경보 정리 효과 측정과 연동
