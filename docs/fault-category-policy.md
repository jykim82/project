# 장애 분류(fault_category) 정책

## 목적
`tb_task_master.fault_category` 는 4값(`고장 / 이상 / 교체 / 점검`)만 허용되며,
각 값의 **적용 조건**과 **분류 경로**를 여기서 명문화한다.
특히 "알람으로만 들어온 건" 과 "사람이 현장 확인 후 등록한 건" 의 경계를
엄격히 구분해 **데이터 신뢰도**를 지킨다.

---

## 4 분류 정의

| 분류 | 상태 | 진입 경로 | 예시 |
|------|------|-----------|------|
| **고장** | 설비 **기능 중단** (작동 불가). 즉시 복구 필요 | **현장 작업자가 확인 후 명시 등록** | "신평 배수지 PLC 고장 등록", "펌프 안 돌아감", "UPS 사망" |
| **이상** | **비정상 신호·수치·통신 관찰**. 아직 완전히 멈추진 않음. 관찰·대응 필요 | 시스템 알람 기반 or 현장 이상 징후 | "전원 튀는 현상", "통신 간헐 끊김", "센서 수치 이상" |
| **교체** | 설비 **교체 작업** (고장 결과 또는 예방) | 교체 완료 후 등록 | "UPS 배터리 교체", "LTE 모뎀 교체" |
| **점검** | **예방 점검·정기 검사** | 점검 일정에 따른 등록 | "연간 정기 점검", "분기 현장 점검" |

## 핵심 원칙

### 1. 알람은 기본 "이상"
- `tb_equipment_alarm_report` 로 자동 감지된 모든 알람은 **기본적으로 "이상"** 범주.
- 통신·네트워크 알람은 False Positive 가능성이 높고(간헐 두절/센서 노이즈 등)
  단독으로 **실제 장애 여부를 확정할 수 없음**.

### 2. "고장" 은 현장 확인이 선행된 경우만
- 작업자가 **현장에서 직접 확인**한 결과만 "고장" 분류 허용.
- 채팅/UI 에서 명시적으로 "고장 등록"/"고장보고" 의도로 입력한 건만 "고장"
  으로 저장.
- **시스템이 알람만 보고 자동으로 "고장" 으로 분류하지 말 것.**

### 3. 자동 경로 없음
- 현재 `tb_equipment_alarm_report` → `tb_task_master` 자동 변환 경로는
  존재하지 않으며, 앞으로도 **만들지 않는다**.
- 알람과 장애 기록의 연결은 `tb_task_master.linked_alarm_*` 필드에 사용자가
  명시적으로 넣는 경우에만 발생 (참고 사양: `memory/feedback_no_auto_alarm_link.md`).

### 4. "통신/네트워크" 키워드 휴리스틱
- 채팅 자연어 파싱 (`chat_fault_record.parse_fault_text`) 이
  사용자의 텍스트에서 "통신", "네트워크", "LTE", "모뎀", "SIM" 같은 단어를
  발견하면 **기본 분류를 "이상" 으로 강제**.
- 단, 사용자가 **"현장 확인"/"직접 확인"/"현장 갔"** 같은 현장 확인 단서를
  함께 기재하면 "고장" 유지 허용 (사용자 명시 의도 존중).

## UI·UX 반영 지침

### 설비 건강성 대시보드 (/monitoring/equipment-health)
- 상단 KPI "고장" / "이상" / "교체·점검" 카드 → 본 정의 그대로 표출
- 숫자만 보고 전체 장애 규모를 판단하지 말 것 — "이상" 은 알람 기반도 포함
  되므로 과다 계상 가능

### 설비 교체 후보 분석 (equipment-status)
- 상태 분류는 `fault_category` 와 별도 (`needs_action / in_progress /
  replacement_candidate / resolved`). 혼동 금지.

### 관리자 UI (/setup/fault-cases)
- 고장 진단 케이스 DB 자체는 분류(category)가 없고 "증상-원인-조치" 만 저장.
  본 정책과 직접 관계 없음.
