# 푸시 알림 계획 (검토안) — 스마트폰 + 로컬 PC

> **상태: 계획 수립 완료, 구현 보류** (2026-07-28 사용자 결정 —
> "계획만 수립하고 향후 구현으로 남길 것"). 이 문서를 근거로 선제 구현하지
> 않는다. 착수 시 본 계획을 출발점으로 상세 설계한다.

목표 두 가지 (사용자 요청):
1. **스마트폰 푸시** — Firebase(FCM) 기반
2. **로컬 PC 푸시** — 웹 브라우저를 열어두지 않아도 받는 알림

---

## 0. 사양 충돌 검토 (필수 선행 판단)

**Firebase(FCM)는 Google 클라우드 서비스다 — 폐쇄망 온프레미스 원칙과
정면 충돌한다** (CLAUDE.md "외부 API·CDN·cloud LLM 의존 금지").

다만 이 제품에는 이미 **외부망 opt-in 전례**가 있다:
- 외부망 통화 TURN 릴레이 (`realtime-comm-spec` — coturn, 이중 토글)
- 지도 CDN opt-in (`offline-map-bundle` — 기본 오프라인, 환경변수로 CDN)

→ 같은 패턴으로 푼다: **기본은 폐쇄망 완결 채널(PC 에이전트), FCM 은
외부망이 허용된 고객만 SITE_SETTING 토글로 opt-in.** 폐쇄망 고객에게
FCM 을 전제한 기능을 팔지 않는다.

**기술적 한계 명시**: 스마트폰 OS 레벨 푸시(화면 꺼진 상태 도달)는 OS
푸시 인프라(FCM/APNs = 클라우드)를 반드시 경유한다. **순수 폐쇄망에서
스마트폰 백그라운드 푸시는 원리적으로 불가** — 폐쇄망 고객의 모바일
대안은 self-hosted 게이트웨이(§2.3) 또는 현장 모드 PWA 폴링(앱이 떠
있을 때만)이다. 계획서에 이 한계를 숨기지 않는다.

## 1. 공통 기반 — 알림 발송 파이프라인 (Phase 0, 두 채널의 전제)

지금 알림은 화면(폴링)이 스스로 가져간다. 푸시는 서버가 **밀어야** 하므로
발송 파이프라인이 선행돼야 한다.

```
[이벤트 소스] → tb_notification_queue → [디스패처 루프] → 채널별 발송
                                              ├ PC 에이전트 (Phase 1)
                                              ├ FCM (Phase 2, opt-in)
                                              └ (기존 웹 벨은 불변)
```

- **이벤트 소스 (P1 범위)**: ① 심각도 '경고' 경보 발생 ② N분 미확인
  에스컬레이션 (`alarm-confirm-audit-spec` P2 와 합류 — 확인 책임 체계의
  후속) ③ 일정 알림 (tb_user_schedule). 반복 경보(채터링)는 접기 규칙
  적용 — 같은 (현장,메시지)는 재발 시 재푸시 억제 창(예: 30분)
- **큐 테이블**: 발송 이력·실패 재시도·감사(누가 어떤 알림을 언제 받았나).
  경보 자체를 다시 쓰는 게 아니라 **발송 사실만** 기록 (알람 테이블 불가침)
- 디스패처는 백엔드 내장 루프 (기존 `_alarm_release_loop` 패턴, cron 불요)

## 2. 채널

### 2.1 Phase 1 — 로컬 PC 에이전트 (폐쇄망 완결, 전 고객 배포 가능 → 우선)

- **트레이 상주 경량 에이전트** (Windows 10/11 대상): 로그인 후 트레이에
  상주, 백엔드 폴링(30s, 기존 벨 주기와 동일) → **Windows 네이티브 토스트**
  표시. 클릭 시 기본 브라우저로 해당 화면 딥링크
- 브라우저 独立 — "웹 접속 없이도"의 답. Web Push 는 부적합: 데스크톱
  Chrome 도 푸시 서비스(FCM) 경유라 폐쇄망 불가 + 브라우저 완전 종료 시
  미수신
- 구현 후보: Python + pystray/win10toast 를 PyInstaller 단일 exe (폐쇄망
  반입 용이, 기존 파이썬 역량 재사용) — 상세는 착수 시 결정
- 인증: 발급형 에이전트 토큰 (운영 PC 단위, 개인 계정 로그인 강제하지
  않음 — 관제실 공용 PC 현실)

### 2.2 Phase 2 — FCM 스마트폰 푸시 (외부망 고객 opt-in)

- `SITE_SETTING.PUSH_FCM_ENABLED` 마스터 토글 (기본 OFF) + Firebase
  서비스 계정 키는 서버 설정 파일 (고객별 프로젝트)
- 수신 앱: **별도 네이티브 앱을 만들지 않는다** — 현장 모드(/field) PWA 에
  FCM Web Push 등록 (Android 우선. iOS 는 PWA 푸시 제약 확인 후 판단)
- 대상 이벤트는 Phase 0 큐와 동일, 사용자별 구독 설정 (현장 담당 시설만 등)

### 2.3 검토 대안 (착수 시 재평가)

- **self-hosted 푸시 게이트웨이 (ntfy/gotify)** — 폐쇄망 내 자체 서버 +
  전용 앱으로 FCM 없이 모바일 백그라운드 푸시 가능 (앱이 서버에 상시
  연결 유지). 폐쇄망 고객의 모바일 요구가 실제로 생기면 FCM 대신 이쪽이
  원칙 정합 — 단 앱 설치·배터리 소모·운영 부담 평가 필요

## 3. 하지 않는 것

- 완전 자동 발송의 무제한 확대 금지 — 푸시 대상 이벤트는 화이트리스트로
  시작 (경고·에스컬레이션·일정). "모든 알람 푸시"는 채터링 사태를 주머니
  속으로 옮기는 것이다 — 반복 억제 창 필수
- 경보 테이블에 발송 상태를 쓰지 않는다 (발송 이력은 큐 테이블 소관)

## 4. 예상 단계 (착수 시)

| 단계 | 내용 | 규모 감 |
|---|---|---|
| Phase 0 | 알림 큐 + 디스패처 + 이벤트 소스 3종 | 중 |
| Phase 1 | PC 트레이 에이전트 + 토큰 인증 + 납품 번들 | 중~대 |
| Phase 2 | FCM opt-in + /field PWA 등록 + 구독 설정 | 중 |

미결정(착수 시 확정): 에이전트 배포 방식(전 PC 수동 설치 vs 공유 폴더),
FCM 프로젝트 소유(고객 vs 구축사), iOS 지원 범위, 에스컬레이션 N분 기준.
